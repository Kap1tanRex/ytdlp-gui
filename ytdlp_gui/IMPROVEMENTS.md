# Топ-5 идей по улучшению yt-dlp GUI

Реалистичные доработки, которые можно внести в текущую архитектуру без
переписывания проекта — с указанием, что именно менять и зачем.

## 1. Автообновление yt-dlp прямо из интерфейса

**Проблема:** YouTube регулярно меняет формат страниц, из-за чего старая
версия `yt-dlp.exe` перестаёт скачивать видео («Unsupported URL», пустой
список форматов). Сейчас обновление возможно только вручную, заменой файла.

**Решение:** yt-dlp умеет обновлять себя сам (`yt-dlp.exe -U`). Добавить на
вкладку «Настройки» кнопку «Проверить обновления», которая в фоновом потоке
запускает `self.ytdlp.run(["-U"])` (метод уже есть в
[`ytdlp_service.py`](services/ytdlp_service.py)) и показывает результат —
текущая версия / новая версия / уже актуальна. После обновления —
`self.ytdlp.locate()` и `Event.TOOLS_READY`.

**Трудозатраты:** низкие, 1 новый метод в `Application` + пара виджетов в
`settings_tab.py`.

## 2. Полноценная работа с плейлистами

**Проблема:** сейчас `InfoService.parse_info` для плейлиста возвращает только
`playlist_count` — список видео внутри не разбирается, скачать можно только
«всё целиком» через `--yes-playlist`. Выбрать конкретные ролики или диапазон
нельзя.

**Решение:** при `_type == "playlist"` разбирать `entries` в список дочерних
`VideoInfo` (или упрощённых записей id/title/url), показывать их в отдельном
списке с чекбоксами, и передавать выбор в yt-dlp через `--playlist-items
"1,3,5-7"`. Это расширение `core/models.VideoInfo` (поле `entries`) и
`core/command_builder.py` (новый аргумент), плюс небольшой виджет в GUI.

**Трудозатраты:** средние — самая объёмная из пяти идей, но полностью
укладывается в существующую модель `DownloadOptions`.

## 3. Повторная попытка при сетевых сбоях

**Проблема:** очередь (`queue_manager.py`) один раз запускает
`ProcessManager.run_job` и при ошибке сразу помечает задание как `FAILED`.
Для типичных временных сбоев (обрыв соединения, `429 Too Many Requests` —
уже распознаётся в [`error_analyzer.py`](core/error_analyzer.py) как
`RATE_LIMITED`/`NETWORK`) это неудобно: приходится пересоздавать задание
руками.

**Решение:** два уровня, оба дёшевы:
- передавать `--retries 10 --fragment-retries 10` в команду yt-dlp
  (`command_builder.build`) — сам yt-dlp уже умеет ретраить на уровне HTTP;
- добавить в `QueueTab` кнопку «Повторить» у проваленных заданий, которая
  клонирует `Job` (тот же `url`/`options`) и кладёт в очередь заново — без
  ручного пересоздания через вкладки.

**Трудозатраты:** низкие.

## 4. Пакетный импорт ссылок

**Проблема:** ссылки можно добавлять только по одной через поле ввода.
Для «скачать 20 видео с канала списком» нет удобного пути.

**Решение:** кнопка «Импорт из файла» рядом с полем URL — открывает `.txt`
(по одной ссылке на строку) и вызывает уже готовый `app.fetch_urls(...)`.
Дополнительно можно принимать вставку многострочного текста в само поле
`url_entry` (разбивать по переносам строк перед вызовом `fetch_url`).
Сервисный и доменный слои менять не нужно — только `main_window.py`.

**Трудозатраты:** низкие.

## 5. Автотесты для core-слоя

**Проблема:** в `ffmpeg_gui` есть `tests/` и `pytest` в зависимостях
(раздел 57 ТЗ), а в `ytdlp_gui` тестов нет вообще. Слой `core/` (
`command_builder.py`, `validator.py`, `models.py`) — чистые функции без
GUI и без сети, идеальный кандидат для модульных тестов, которые ловят
регрессии при доработке (например, пунктов 1–4 выше) до реального запуска
yt-dlp.

**Решение:** добавить `tests/test_command_builder.py` (проверка сборки `-f`,
флагов субтитров/эмбеддинга по разным `DownloadOptions`),
`tests/test_models.py` (форматирование размеров/длительности,
`MediaFormat.describe()`), `tests/test_validator.py`. Достаточно 15–20
тестов без моков процессов — `command_builder.build()` не запускает
subprocess, только строит список аргументов.

**Трудозатраты:** низкие-средние, но самая высокая отдача по надёжности
на вложенное время.
